Agentic Systems Series

Build the system. Earn the agent.

An AI agent is not a model with a longer prompt. It is a system that lets a model choose actions inside a controlled loop. That freedom can solve ambiguous work—but it also adds latency, cost, and new ways to fail. Your first design decision is therefore not which model to use. It is how much agency the task has actually earned.

The best agent architecture often begins by deleting the parts that do not need an agent.

01—Choose

Start below the agent#

Suppose a customer writes: “Order 4821 arrived late and damaged. Refund shipping, replace the item, and make sure it arrives before Friday.” The message is messy. The policy is conditional. Several systems hold the facts. That makes it a useful test—not an automatic argument for autonomy.

Code Fixed schema, fixed transformation, exact output.
Workflow Known steps and branches, including model calls.
RAG Unstructured question, retrieval, grounded answer.
Agent The system must decide which actions come next.

Agency#

Decision 01 · Control surface
Agency is the freedom to select and sequence actions, not the presence of an LLM.

Anthropic draws a useful line between workflows, where code predetermines the path, and agents, where the model directs its own process and tool use.[2] The boundary is practical rather than metaphysical. A system can classify the message with a model, retrieve policy with RAG, and still execute a deterministic refund workflow.

Give the model control only where enumerating every branch would be brittle. Keep identity checks, refund ceilings, inventory reservations, and payment mutations in deterministic code. This hybrid is usually easier to test than a loop that asks the model to rediscover business rules on every turn.

Choose the least autonomous system that can complete the task reliably.Every additional degree of freedom becomes another behavior you must evaluate, observe, and constrain.
02—Anatomy

Separate reasoning from authority#

A production agent is a small control system. The model proposes what to do. Tools expose permitted operations. State carries relevant facts. Orchestration enforces the loop. Policies and humans decide what the model may not decide alone.

Model#

Component 01 · Decision engine
Choose enough reasoning capability for the hardest decision, then route simpler work elsewhere.

The model interprets the request, weighs available context, and proposes a next action. It should not be your database, policy engine, or permission system. Model selection is an empirical decision: start with a capable baseline, build evaluations, then test whether smaller or faster models preserve the required behavior.[1]

The original draft compared named models with a dated leaderboard. That creates false precision. A benchmark mean does not tell you whether a model will correctly handle your refund policy, tool schemas, error states, or latency budget. Your evaluation set should.

Tools#

Component 02 · Controlled action
A tool is a typed capability with a narrow contract, explicit errors, and limited authority.

Tools let the agent fetch Order 4821, read the damage policy, check replacement stock, calculate an allowed refund, or submit an approved mutation. Clear names, precise parameter descriptions, validated inputs, and useful error responses matter because the model sees the interface—not your intent.

Model Context Protocol standardizes how hosts connect models to focused servers that expose tools and contextual data, but a common protocol is not a security boundary by itself.[3] Authentication, authorization, least privilege, logging, and user consent still belong to your application.

State#

Component 03 · Relevant memory
Store facts because the next step needs them—not because “agents need memory.”

Short-term state may include the customer’s verified identity, retrieved policy version, tool results, pending actions, and remaining budget for this run. Long-term memory is a separate product decision. Persisting preferences or outcomes can improve continuity, but it creates retention, privacy, deletion, and stale-data obligations.

For Order 4821, the durable record should live in the order and support systems. The agent’s working context should reference those sources of truth. A vector store is useful for semantic retrieval; it is not an authoritative ledger.

03—Execute

Advance one evidenced step at a time#

The useful loop is not “think until done.” It is observe, choose a permitted action, execute it, record the result, and reassess. ReAct research formalized the value of interleaving reasoning and actions; production systems add budgets, structured tool calls, and stop conditions.[6]

01ObserveParse the request and current state.
02ChooseSelect one allowed next action.
03ActCall a tool with validated arguments.
04ReassessUse the result or stop safely.

Orchestration#

Component 04 · Runtime loop
The loop owns budgets, transitions, retries, pauses, and termination.

Orchestration converts a model response into a controlled transition. It validates the proposed tool call, checks authorization, executes the operation, appends the result to state, and asks what comes next. It also decides when the run is done.[7]

next_state = transition(current_state, validated_action, tool_result)

Set explicit ceilings for turns, wall-clock time, tokens, tool calls, retries, and monetary exposure. A retry should address a transient failure, not repeat the same invalid plan. After the ceiling, return a safe partial result or escalate with the evidence already collected.

04—Operate

Production begins at the boundary#

A demo proves that a path can work. Production engineering asks what happens when the model chooses the wrong tool, a dependency times out, retrieved text is hostile, the customer changes intent, or the same request is replayed.

Boundaries#

Production 01 · Before launch
Constrain authority, then make every consequential transition observable and reversible.

NIST’s Generative AI Profile frames risk management across design, development, deployment, use, and evaluation rather than treating safety as a final filter.[4] Apply that lifecycle to the agent’s actual capabilities. A support agent that drafts replies has a different risk surface from one that moves money or reserves inventory.

Keep deterministic

  • Authorization: who may read or mutate Order 4821.
  • Business invariants: refund ceilings and inventory consistency.
  • Idempotency: a replay must not issue a second refund.
  • Audit records: inputs, decisions, approvals, and effects.

Let the model propose

  • Interpretation: connect the customer’s language to task intent.
  • Action selection: choose among currently permitted tools.
  • Recovery: revise a plan after a meaningful tool error.
  • Communication: explain the verified outcome clearly.
A human approval screen must show the proposed action, evidence, policy basis, and irreversible effect.“Approve” is not informed oversight if the reviewer must reconstruct the run from raw logs. A robust runtime pauses before the tool call and resumes the same saved run after approve or reject.[8]

Evidence#

Production 02 · Evaluation
Measure the decisions and effects that matter, not whether the final answer sounds plausible.

Build evaluations from representative tasks, edge cases, and known failures. Grade intermediate behavior: policy retrieval, argument validity, tool choice, refusal, escalation, and final state. OpenAI’s evaluation guidance recommends task-specific evals, logging, automation where possible, and continuous evaluation as the system changes.[5]

For Order 4821, a polished apology is not success if the system refunds twice, invents Friday delivery, or replaces the wrong SKU. Your strongest checks inspect deterministic outcomes: the correct order was accessed, policy version was recorded, the refund stayed within limits, and the reservation actually exists.

Complexity#

Production 03 · Scale carefully
More agents add coordination work before they add useful specialization.

Start with one agent and a small tool set. OpenAI’s practical guide explicitly recommends maximizing a single agent before splitting work across multiple agents because added agents introduce overhead and complexity.[1] Add a specialist only when its separate instructions, tools, context, or evaluation boundary are genuinely easier to maintain.

A multi-agent design is not automatically more resilient. It creates more prompts, handoffs, context boundaries, failure modes, and token traffic. Anthropic’s production account finds the pattern strongest for breadth-first, parallelizable research and a poor fit when agents must share context or coordinate dependencies.[9] Splitting Order 4821 among five conversational roles would mostly create coordination latency around one shared transaction.

Scale the runtime before you scale the cast.Queues, checkpoints, idempotent tools, tracing, and backpressure usually matter sooner than another agent persona.
05—Sources

Sources and further reading#

The article favors durable architectural guidance over model rankings. These sources define the agent patterns, interface standards, evaluation practices, and risk controls behind the recommendations.

  1. OpenAI — A Practical Guide to Building Agents. Guidance on agent foundations, model and tool selection, orchestration, guardrails, and the recommendation to maximize a single agent before adopting multi-agent complexity. Read the guide
  2. Anthropic — Building Effective Agents. An engineering distinction between predefined workflows and model-directed agents, with composable patterns and advice to begin with the simplest solution. Read the article
  3. Model Context Protocol — Architecture and Tools, specification 2026-07-28. The current official protocol specification separates host policy and orchestration from focused servers, and defines discoverable tools with JSON Schema contracts. Read architecture · Read tools
  4. NIST — Artificial Intelligence Risk Management Framework: Generative Artificial Intelligence Profile. A cross-sector companion to the AI RMF for identifying and managing generative-AI risks across the lifecycle. Read NIST AI 600-1
  5. OpenAI Developers — Evaluation Best Practices. Official guidance on defining objectives, collecting datasets, choosing task-specific metrics, running comparisons, and continuously evaluating changes. Read the documentation
  6. Yao et al. — ReAct: Synergizing Reasoning and Acting in Language Models. The original paper describing an interleaved reasoning-and-action pattern for interacting with external environments. Read the paper
  7. OpenAI Agents SDK — Running Agents. Runtime documentation for the model-call, tool-call, handoff, observation, and termination loop, including turn limits and state-management options. Read the documentation
  8. OpenAI Agents SDK — Human in the Loop. A concrete pause, inspect, approve-or-reject, serialize, and resume pattern for sensitive tool calls. Read the documentation
  9. Anthropic — How We Built Our Multi-Agent Research System. A first-party production report on parallel research, separate context windows, coordination cost, token use, evaluation difficulty, and poor-fit conditions. Read the report
